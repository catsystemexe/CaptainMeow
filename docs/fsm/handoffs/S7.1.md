# S7.1 — Transition movement correctness and retained Dev UI FSM inspection

## Goal

Fix two user-observed S7 regressions without beginning S8:

1. `fsm.smart_orbit_half` displayed `retreat` after `orbit → retreat`, but movement could continue to look like orbit movement instead of `straight.charge`.
2. Dev UI cleared the FSM graph/runtime details after the inspected FSM enemy was removed.

## Movement root-cause proof

Inspection confirmed canonical content was correct:

- `fsm.smart_orbit_half.enter` uses `smart.range.close`.
- `fsm.smart_orbit_half.orbit` uses `smart.orbit.half`.
- `orbit → retreat` is a `timeInState` transition at `1.6s`.
- `fsm.smart_orbit_half.retreat` uses `straight.charge`.

The risky runtime point is the transition tick in `EnemySystem`: `updateResolvedFsm()` can perform formal entry and replace `fsmRuntime.movement`. The movement owner must then execute the freshly assigned `fsmRuntime.movement`, not any movement runtime reference captured before the update. S7.1 makes that invariant explicit at the call site and regression-tests the same-tick execution object.

## Runtime fix

`EnemySystem` now treats `updateResolvedFsm()` as the boundary after which the active movement runtime must be reacquired from the runtime snapshot. The same tick then executes that current runtime, preserving:

- single position integration in `EnemySystem`,
- non-FSM movement behavior,
- group movement suppression,
- transition timing,
- state-age semantics,
- combat and lifecycle behavior.

No canonical content was changed.

## `fsm.smart_orbit_half` before/after

Before the fix, the observed runtime state could show `retreat` while the visible movement still looked like the previous `smart.orbit.half` orbit path.

After the fix and regression coverage:

- the `orbit` tick transitions to `retreat`,
- formal entry replaces the movement runtime object,
- the new runtime base is `straight.charge`,
- behavior-local orbit state is not reused,
- the first retreat tick executes the fresh `straight.charge` runtime,
- later retreat ticks continue charge-compatible horizontal retreat rather than orbit motion,
- position integrates exactly once.

## Other transitions audited

The new transition smoke audits movement-changing canonical transitions for:

- `fsm.smart_orbit_repeat`,
- `fsm.smart_aligner`,
- `fsm.hover`,
- `fsm.zigzag`.

For time-driven transitions whose source and target movement presets differ, it verifies formal entry replaces the movement runtime and that same-tick execution uses the target runtime.

## Proof formal entry replaces movement runtime

`FsmTransitionMovement.smoke.ts` asserts:

- source runtime identity differs from target runtime identity,
- source behavior-local state differs from target behavior-local state,
- target runtime base preset matches the canonical target state movement,
- debug snapshot movement preset matches the active runtime movement preset.

## Retained Dev UI data model

S7.1 adds a Dev UI-owned immutable inspection model:

```ts
interface RetainedFsmInspection {
  graph: readonly unknown[];
  runtime: FsmDebugSnapshot;
  status: "live" | "ended";
  endReason?: "despawned" | "removed";
  typeId?: string;
  hpLabel?: string;
  position?: PositionDebug;
}
```

The retained data clones graph rows and `FsmDebugSnapshot` data. It does not retain a mutable entity object and does not use `localStorage`.

## Live → ended behavior

The existing Enemy Lab refresh path still drives updates. When a selected/live FSM entity resolves, Dev UI refreshes the retained snapshot with `status: "live"`. When the selected entity no longer resolves after cleanup/removal, Dev UI keeps the last retained immutable snapshot, changes the status to `"ended"`, and displays an `ENTITY REMOVED` status line while keeping the final graph and highlighted state visible.

## Next-spawn and explicit-selection policy

The next live FSM spawn/selection replaces the retained ended snapshot. A non-FSM selection does not produce a live FSM snapshot, so stale FSM data is not presented as live.
