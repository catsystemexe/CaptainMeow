# S11 — FSM preview workflow, runtime diagnostics, and integration closeout

## Goal
Complete the FSM roadmap with an Enemy Lab preview/test workflow that can run valid unsaved drafts without persistence, run saved presets from the combined registry, display runtime diagnostics and a bounded transition trace, and leave normal gameplay spawning unchanged.

## Starting S10 state
S10 already provided schema-v1 built-ins, user preset persistence, a combined built-in/user registry, immutable built-ins, runtime Enemy Lab mounting, preset management, isolated form authoring drafts, validation-gated Save, and no node graph or UI redesign.

## Preview session model
`src/dev/FsmPreviewSession.ts` owns one preview entity at a time. Its public operations are `startDraftPreview`, `startPersistedPreview`, `restart`, `stop`, `refresh`, and `current`. Snapshots report source, status, preset id, entity ref, runtime debug snapshot, diagnostics, started tick, ended reason, position/removal state, and trace.

## Draft preview resolution
Draft preview clones the authoring draft, normalizes through the existing FSM normalizer, validates through existing validation plus movement catalog checks, rejects errors, allows warnings, resolves an immutable non-persisted snapshot, and never inserts the result into built-in/user/combined registries or storage.

## Persisted preview flow
Saved preview resolves the selected preset from `CONTENT.fsmPresets`, so built-ins and saved user presets use the same combined persisted registry as ordinary gameplay.

## Spawn integration
`SpawnSystem` now accepts a narrow dev/test `resolvedFsmPresetOverride` on enemy spawn payloads and exposes `spawnPreviewEnemy()` for preview callers. Ordinary gameplay still resolves by id/default content and does not provide this override.

## Start/restart/stop semantics
Starting a preview replaces any running preview. Restart marks the current preview for kill and spawns a fresh entity from the retained source. The deterministic placement is fixed by preview session dependencies and defaults to a stable right-side logical position.

## Cleanup ownership
Stop uses `EntityStore.markKill`; actual removal remains owned by normal Cleanup. Repeated Stop is safe. Ended snapshots are retained after despawn/removal until the next preview replaces them.

## Runtime diagnostics
Enemy Lab displays preview source/status, preset id, active state label/id, state index, state age, entry count, movement base preset, modifier types, movement suppression, combat mode, active attack profile, entity position, and pending/removed state from `getFsmDebugSnapshot()` and store state.

## Transition trace
The preview session derives a fixed-size transition trace from observed runtime state id / entry-count changes. It includes initial spawn entry, formal transitions, self-transitions, bounded retention, and no console spam or gameplay event machinery.

## Validation gates
Draft preview is blocked for read-only built-ins and blocked when validation has errors, including dangling transitions, invalid initial state, unknown movement preset, invalid modifier params, unknown attack profile, immediate action cycle, duplicate state id, or invalid lifecycle action. Warnings do not block preview.

## Normal gameplay isolation
Draft preview does not save, does not write localStorage, does not mutate the user preset store, does not alter built-ins, does not appear in combined registry lists/export/storage, and does not change the normal spawn selector. Saved preview and ordinary spawn continue to use persisted resolved presets.

## Enemy Lab integration
A compact Preview section was added to the existing Enemy Lab with `Preview Draft`, `Preview Saved`, `Restart`, `Stop`, status, runtime diagnostics, and transition trace. The existing layout/style was preserved; no graph canvas, draggable graph, or standalone redesign was added.

## End-to-end test coverage
New smokes cover preview session lifecycle, draft preview isolation, runtime diagnostics/trace, Enemy Lab preview controls, and the integrated S1–S11 workflow from built-in duplication through draft validation, ephemeral preview, save, combined registry resolution, normal runtime use, transition, combat, lifecycle despawn, debug snapshot, export, built-in immutability, and deterministic rerun.

## Final architecture audit
Verified: schema v1 remains canonical for built-ins; built-ins remain immutable; user presets persist separately; combined registry ordering/source rules remain deterministic; runtime entities use resolved snapshots; transition timing/runtime semantics were not changed; movement/combat/lifecycle reset and despawn policies remain in FSM runtime/SpawnSystem; preview drafts are ephemeral; normal spawn remains persistence-backed; preview performs no per-tick storage/registry/raw JSON lookup; no new simulation `Math.random()` was added by the preview controller; no duplicate position integration owner was introduced; no state-name runtime semantics, hidden built-in migration path, node graph, or UI redesign was added.
