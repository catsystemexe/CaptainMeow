# U1.4.7 — Authoritative Speed, Diagnostics content, and initial Preset lifecycle

## Confirmed browser findings

Browser reports after U1.4.6 were authoritative: Count, state Behavior, state Formation, and state Elasticity worked, while Basic Setup Speed and state Speed × did not visibly affect runtime displacement, Runtime Diagnostics opened as an empty external panel, and the current preset selector did not open on the first click until `+` caused a later render/lifecycle path.

## Speed current calculation audit

| Stage | File/function | Input | Output | Can overwrite prior speed? | Observed value |
|---|---|---|---|---|---|
| Basic Setup Speed UI | `DevSummoner.ts` `fsmBaseSpeedSlider` / `editFsmBasicSetupDraft` | slider value in px/s | `preset.basicSetup.baseSpeed` on the authoring draft | No | draft contains the selected base speed |
| Draft preset | `FsmPresetEditorModel.setBasicSetup` and `resolveEphemeralFsmPreset` callers | authoring draft | resolved override definition | No | override includes `definition.basicSetup.baseSpeed` |
| Resolved FSM preset | `resolveFsmPreset` | schema basic setup + graph states | `runtime.preset.definition.basicSetup.baseSpeed`, resolved states | No | runtime has base speed and canonical state fields |
| State Speed × UI | `DevSummoner.ts` `stateSpeedSlider` / `FsmPresetAuthoringModel.setLabFormationField` | slider scalar | active state `speedMultiplier` | No | canonical `state.speedMultiplier` exists |
| Effective speed | `fsmEffectiveSpeed` | `basicSetup.baseSpeed`, active `speedMultiplier` | `baseSpeed * speedMultiplier` | No | value was computed but later applied by normalization |
| Movement preset output | `executeFsmMovement` | behavior preset parameters (`speedX`, `speedY`, sine modulation, charge speed, hold) | target position for this tick | Yes, it encodes preset absolute speed in the target delta | raw preset velocity existed before final velocity write |
| Final velocity writer | `EnemySystem.update` for single, `EnemyGroupRegistry.updateAnchors` for groups | target, dt, effective speed | `entity.vel` / `group.vel` | Yes | U1.4.6 normalized target direction to effective speed |
| Integration | `EnemySystem.update` and `EnemyGroupRegistry.updateAnchors` | final velocity | `pos += vel * dt`, `anchor += vel * dt` | No | integration uses velocity directly |

Answers:

1. Basic Setup Speed is stored as `basicSetup.baseSpeed`.
2. It represents pixels per second baseline runtime movement speed.
3. State Speed × is stored as canonical state `speedMultiplier`, with legacy fallback `formationOverride.speedMultiplier`.
4. `effectiveSpeed` is computed in `fsmEffectiveSpeed`.
5. Final single `vx/vy` is written in `EnemySystem.update`; final group-anchor `vx/vy` is written in `EnemyGroupRegistry.updateAnchors`.
6. For group members, `applyMemberCohesion` later overwrites member entity velocity so members chase the anchor; it does not overwrite group anchor velocity. For singles, non-FSM behavior is skipped and does not overwrite FSM velocity.
7. Single runtime and group anchor both use `updateResolvedFsm` → `executeFsmMovement` → `velocityFromFsmTarget`, but they have separate final writer call sites.
8. Speed is applied after movement preset evaluation.
9. Before this fix, non-zero movement output was normalized to `effectiveSpeed`, which erased intentional magnitude modulation from sine/charge-style preset output.
10. Position integration uses final velocity directly (`vel * dt`), not a separate scalar.
11. Built-in movement presets return absolute per-tick target deltas from params like `speedX`/`speedY`; U1.4.6 normalization could override the raw magnitude instead of scaling it compatibly.
12. Draft Basic Setup Speed is present in the resolved override at runtime.
13. State Speed × is present in the active runtime state.
14. Diagnostics did not show post-resolution/post-write speed values before U1.4.7; it now reports base, multiplier, effective, raw velocity, final velocity, reference speed, and integrated delta from the authoritative write path.

## Single runtime call graph

`DevSummoner` Basic Setup / State controls → authoring draft → resolved override on spawn → `SpawnSystem` creates enemy FSM runtime → `EnemySystem.update` calls `updateResolvedFsm` → `executeFsmMovement` evaluates movement preset target → `fsmEffectiveSpeed` computes `basicSetup.baseSpeed * state.speedMultiplier` → `fsmMovementReferenceSpeed` reads preset reference speed from movement params → `velocityFromFsmTarget` scales raw preset velocity → `EnemySystem.update` writes `e.vel.x/y` and speed diagnostics → `EnemySystem.update` integrates `e.pos.x/y += e.vel.x/y * dt`.

## Group runtime call graph

`DevSummoner` Basic Setup / State controls → authoring draft → resolved group override on spawn → `SpawnSystem` creates `EnemyGroupRegistry` group FSM runtime → `EnemySystem.update` calls `EnemyGroupRegistry.updateAnchors` before member iteration → `updateResolvedFsm` updates active state → `applyStateFormation` updates group formation fields → `executeFsmMovement` evaluates anchor movement target → `fsmEffectiveSpeed` computes speed → `fsmMovementReferenceSpeed` reads reference speed → `velocityFromFsmTarget` scales raw anchor velocity → `EnemyGroupRegistry.updateAnchors` writes `group.vel.x/y` and speed diagnostics → anchor integrates `group.anchor.x/y += group.vel.x/y * dt` → member entity iteration uses `applyMemberCohesion` to follow the anchor.

## Final authoritative velocity writer

Single enemies: `EnemySystem.update` writes `e.vel.x` and `e.vel.y` immediately after `velocityFromFsmTarget`.

Group anchors: `EnemyGroupRegistry.updateAnchors` writes `group.vel.x` and `group.vel.y` immediately after `velocityFromFsmTarget`.

## Speed root cause

U1.4.6 fixed where speed data was read, but the final conversion from movement target to velocity used direction normalization whenever `effectiveSpeed` was present. That made tests that only looked at straight magnitude pass, but it treated every non-zero movement preset vector as a direction-only vector and could hide browser-visible behavior when built-ins already encoded absolute velocities or modulation. Diagnostics also did not expose actual raw/final/integrated values, so the previous tests did not prove the authoritative write path.

## Speed fix

`velocityFromFsmTarget` now computes raw movement velocity from the movement preset target (`dx/dt`, `dy/dt`) and, when the movement preset exposes a reference speed, scales the raw velocity by `effectiveSpeed / movementPresetReferenceSpeed`. Straight drift, straight charge, and sine keep their direction and pattern while Basic Setup Speed and state Speed × scale actual displacement. Legacy no-reference fallback still normalizes to `effectiveSpeed` for compatibility.

## Pattern-preserving scaling strategy

The selected model is:

```text
rawVelocity = (movementTarget - currentPosition) / dt
runtimeSpeedScale = effectiveSpeed / movementPresetReferenceSpeed
finalVelocity = rawVelocity * runtimeSpeedScale
```

`movementPresetReferenceSpeed` is derived from movement preset params (`hypot(speedX, speedY)` or `abs(speed)`). `none.hold` has no non-zero raw velocity and remains zero. Sine keeps its vertical modulation because the entire raw vector is scaled rather than normalized.

## Actual displacement proof

`FsmSpeedAuthoritativeRuntime.smoke.ts` verifies actual integrated position/anchor deltas, not just intermediate speed values:

- single straight base 50/100/200 produces 50/100/200 px/s displacement magnitude;
- group anchor straight base 50/100/200 produces 50/100/200 px/s anchor displacement magnitude;
- state multipliers 0.5/1/2 produce 50/100/200 px/s at base 100 for both single and group;
- sine base 50 to 200 preserves the pattern while the forward component scales 4×;
- charge scales to the requested baseline instead of using the built-in absolute charge magnitude;
- hold remains zero.

## Diagnostics empty-panel root cause

The diagnostics side panel was reparented to `document.body`, but `refreshEnemyLab()` searched from `this.panel` with `this.panel?.querySelector("#ds-fsm-runtime-diagnostics-body")`. The visible body-level panel therefore existed, but the refresh loop wrote to no node.

## Diagnostics content binding fix

`refreshEnemyLab()` now resolves the stable body-level diagnostics content by `document.getElementById("ds-fsm-runtime-diagnostics-body")`. The implementation keeps one diagnostics root, one content child, and the existing single refresh timer. Runtime diagnostics now include speed fields populated from the authoritative velocity writer.

## Preset initial-click root cause

The compact select popover list was created as a child of the compact select root while the root is moved between wrappers during initial FSM-mode layout. Pressing `+` caused a later render/lifecycle path where the popover happened to behave correctly. The initial lifecycle still had a fragile root-local popover attachment path.

## Preset lifecycle fix

The compact select now appends its fixed-position listbox to `document.body` at construction, while retaining the existing single button listener, document outside-click listener, resize repositioning, and cleanup removal. This makes the first click after fresh mount open the populated side popover without requiring `+`, and prevents duplicated popovers/listeners across rerenders.
