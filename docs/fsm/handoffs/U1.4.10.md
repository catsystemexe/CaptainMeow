# U1.4.10 — Stable state editing and high-speed follow

## Confirmed A3 findings

U1.4.10 implements the narrow A3 fixes: the apparent reset during state edits was caused by the FSM state editor subtree being rebuilt during active input, Speed was hard to verify because world motion, screen motion, hold movement, and group-member cohesion were not separated in diagnostics, and high Speed plus Follow could keep group members in saturated catch-up against distant historical targets.

## State-editor rerender root cause

The state Spacing, Elasticity, Follow, and Speed × sliders shared an `input` handler that mutated the authoring draft and immediately called the full `renderPresetEditor()` path. That full render clears/rebuilds the state list and reattaches the selected editor section, so the active range input could be detached/reparented while the pointer gesture was still in progress.

Trigger steppers had the same practical issue because their click commit path performed the full rerender immediately.

## Live input strategy

State slider `input` events now update the authoring model immediately and update only local status/diagnostic UI. They do not call the structural FSM Lab rerender while the user is dragging or stepping the control. The same input DOM node remains attached through repeated `input` events, and dirty/save state updates immediately.

Trigger numeric steppers update their model and local status without immediately rebuilding the editor subtree, so repeated numeric stepping keeps the active stepper nodes stable.

## Commit-time rerender strategy

State sliders perform the full structural rerender on commit-oriented events: `change`, `pointerup`, and `blur`. This reconciles normalized values and surrounding row state after the active edit is complete, while preserving existing expand/collapse behavior and final model semantics.

Behavior, Shape, and Trigger type controls still use committed selection changes and may rerender structurally.

## Speed diagnostics model

Runtime diagnostics now carry these authoritative speed fields for single enemies and group anchors:

- Basic Speed
- State Speed ×
- Effective Speed
- Reference Speed
- Raw velocity X/Y
- Final world velocity X/Y
- World delta/frame
- World speed magnitude
- Screen velocity X/Y
- Screen delta/frame
- Screen speed magnitude

The fields are recorded at the authoritative movement write sites in `EnemySystem` and `EnemyGroupRegistry`.

## World versus screen speed

Screen diagnostics use the actual screen-space relationship `screenX = worldX - scrollX`. Per-frame screen delta is recorded as world integrated delta minus measured scroll delta, and screen velocity is recorded from that measured delta over `dt`. This makes autoscroll-visible movement distinct from world velocity.

## Member cohesion diagnostics

Group member diagnostics now report:

- member slot
- Follow delay
- target position
- distance to target
- correction velocity X/Y
- correction speed
- catch-up cap
- saturation flag
- overshoot-prevention flag
- anchor speed
- response time

Group anchor diagnostics summarize anchor speed, max member target distance, max member correction speed, saturated member count, Follow, and Elasticity.

## High-speed stutter root cause

The anchor Speed path was already authoritative and linear. The stutter was in member catch-up: high effective anchor speed and Follow create large spatial gaps to historical targets, while the old fixed catch-up cap could leave members saturated for many frames and repeatedly flip correction direction around moving targets.

## Catch-up formula

Member correction now uses bounded convergence toward the target:

```text
desiredDelta = target - memberPosition
distance = |desiredDelta|
responseTime = 0.08 + (elasticity / 10) * 0.22 seconds
anchorSpeed = |groupAnchorVelocity|
catchUpCap = min(2400, max(configuredCap, anchorSpeed * 1.35, distance / responseTime))
correctionSpeed = min(distance / dt, catchUpCap)
correctionVelocity = normalize(desiredDelta) * correctionSpeed
```

Units are pixels and seconds. `configuredCap` is the existing normalized cohesion max catch-up speed, so legacy cohesion limits still provide the floor.

## Overshoot prevention

If the remaining target distance can be covered in the current fixed tick, correction velocity is set so the integration step lands exactly on the target. If the cap is lower than the one-tick target speed, velocity is capped and the member advances toward the target without exceeding the remaining distance. The tested invariant is:

```text
|correctionVelocity| * dt <= distanceToTarget
```

## Follow compatibility

Follow remains time-based. Timestamped anchor history, linear interpolation, per-member delay, bounded capacity, and state-transition history preservation were not changed.

## Elasticity compatibility

Elasticity still changes softness. It maps to a bounded response time used by the dynamic catch-up calculation. Higher Elasticity uses a longer response time while the dynamic cap prevents Elasticity from making members fundamentally unable to follow high-speed anchors.
