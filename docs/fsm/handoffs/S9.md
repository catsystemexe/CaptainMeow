# S9 — Enemy Lab preset management editor MVP

## Goal

S9 adds the first usable Enemy Lab UI for managing FSM presets without adding graph/node editing. It exposes the S8 combined built-in/user registry, user preset persistence, import/export, diagnostics, recovery controls, and DevSummoner selection for spawning user presets.

## Starting S8 APIs

S9 builds on `UserFsmPresetStore` as the only persistence boundary. The UI/model uses `registry()`, `list()`, `get()`, `upsert()`, `rename()`, `delete()`, `clear()`, `importJson()`, `exportJson()`, `inspectRawStorage()`, and `diagnostics()`.

## Editor model/controller

`src/dev/FsmPresetEditorModel.ts` owns UI-domain behavior. It lists combined presets, tracks `selectedId`, exposes a draft with `originalId`, `id`, `label`, `dirty`, and `source`, and routes every write through `UserFsmPresetStore`.

## Preset list behavior

The list is derived from `store.registry().list()` only. Built-ins appear first in canonical registry order, and user presets appear after them in deterministic ID order. Each row carries source, read-only, state-count, and validation metadata.

## Built-in/user permissions

Built-ins are inspectable, selectable, spawnable, and duplicable, but not renamed, deleted, or saved over. User presets are mutable through store APIs. Store-level guards reject built-in rename/delete attempts, so read-only behavior is not only a disabled UI affordance.

## Create/duplicate/rename/delete behavior

- New preset creates deterministic `fsm.user.new`, then `-2`, `-3`, etc. when needed.
- Duplicate creates `<source-id>-copy`, then `-copy-2`, preserving state IDs and transition targets while changing only preset ID/source/label.
- Rename edits user preset ID and label through transactional `UserFsmPresetStore.rename()`.
- Delete requires confirmation and selects the previous list neighbor or first built-in after success.

## Dirty/save/cancel policy

Selecting a preset loads a fresh draft. Built-ins never become writable. Save is enabled only for dirty user drafts; Cancel discards draft edits and reloads persisted values. Selection changes explicitly discard unsaved draft edits; S9 does not autosave keystrokes.

## Import/export UI behavior

The UI accepts pasted JSON and passes it directly to `UserFsmPresetStore.importJson()` with `reject`, `replace-user`, or `rename` collision policy. It displays imported diagnostics and selects the first imported preset on success. Export selected exports the selected user preset; export users exports all user presets and excludes built-ins.

## Diagnostics and recovery UI

Diagnostics from validation, storage, collision handling, migration, and recovery are shown in the Enemy Lab panel. Recovery controls expose raw storage text, `Clear users`, and store-backed corrupt-storage reset behavior through `clear()`. Destructive actions require confirmation and never affect built-ins.

## User-preset spawn integration

DevSummoner now refreshes a spawn selector from `CONTENT.fsmPresets.list()`. User presets are selected/spawned through the same combined registry path as built-ins. Spawn payload construction remains a simple `behaviorPresetId` handoff; no per-spawn storage read is added.

## Known pre-existing failures

The broader `npm run smoke` suite still has the documented pre-existing `BombExplosionChain.smoke.ts / DamageSystem.rules.onExplosion` failure. S9 did not repair or rerun that unrelated full-suite failure.

## Explicitly deferred S10 work

S9 does not add draggable nodes, canvas editing, transition-line editing, state creation/deletion, movement/combat/lifecycle deep editors, or runtime semantic changes.

## Risks and concrete inputs for S10

- S10 should build state/transition authoring on top of `FsmPresetEditorModel` rather than adding direct storage access to UI code.
- A richer dirty-state prompt may be needed before graph editing.
- Export/import controls are text-area based MVPs; S10 may add file download/upload wrappers while still using S8 formats.
- User presets are selectable for spawn, so graph editing must keep validation strict before save.
