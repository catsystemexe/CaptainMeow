# U0.2 — Browser group FSM selection fix

## Goal

Fix the real Enemy Lab browser group-spawn selection path so group members receive the currently selected `fsmPresetId` while retaining selected Type/appearance and group movement ownership.

## Confirmed browser behavior

U0 and U0.1 made the direct spawn contracts correct, but the browser group flow still had a UI-path gap: the group controls were shown while the shared FSM selector lived inside the single-enemy controls. In group mode, the selector could be hidden from the user even though the button handler read it.

## Exact root cause

The actual group Spawn button did read `fsmSpawnSelect.value`, but `fsmSpawnSelect.root` was appended under `enemyControls`. `refreshModeButtons()` sets `enemyControls.style.display = "none"` in group mode and `groupControls.style.display = "flex"`, so the FSM selector was not part of the visible group-spawn DOM path. The real browser group path therefore did not provide a reliable group-mode selector interaction even though helper-level payload tests passed.

A second browser-path issue was found while reproducing user presets: `refreshFsmSpawnSelect()` populated options from the `CONTENT.fsmPresets` combined registry object captured at content-load time. That registry object's `get()` closure can resolve newly created user presets, but its captured `list()` snapshot does not include later user presets. The actual selector therefore could miss user FSM options created after load. The patch uses the live `CONTENT.userFsmPresets.registry()` list/source for the selector.

## Why U0 passed

U0 tests verified the direct `createDevSummonerSpawnPayload(...)`/`createDevSummonerGroupSpawnPayload(...)` contracts and SpawnSystem explicit `fsmPresetId` precedence. They did not mount DevSummoner, switch to group mode, inspect the visible DOM path, click the actual group button, or prove that the group-mode UI exposed the same FSM selector that the click handler reads.

## Why U0.1 passed

U0.1 added direct helper/event/runtime group coverage and proved SpawnSystem forwards `SPAWN_ENEMY_GROUP.fsmPresetId` into every member. Its DevSummoner smoke still called `createDevSummonerGroupSpawnPayload(...)` directly, so it bypassed the actual DOM mode toggle, the shared compact FSM selector, its option source, and the browser Spawn Group click listener.

## Real DOM/button/event path

```text
DevSummoner.init()
→ shared FSM compact selector `#ds-fsm-preset`
→ selector now appended to the shared spawn section, not hidden single-enemy controls
→ user clicks Group mode button
→ group controls become visible and shared FSM selector remains visible
→ user selects Type in `#ds-group-enemy`
→ user selects group movement preset in `#ds-group-movement-preset`
→ user selects FSM preset in `#ds-fsm-preset`
→ actual Spawn Group button listener reads current `fsmSpawnSelect.value`
→ createDevSummonerGroupSpawnPayload({ ..., fsmPresetId })
→ bus.emitNext(EventType.SPAWN_ENEMY_GROUP, payload)
→ SpawnSystem SPAWN_ENEMY_GROUP handler
→ per-member spawnEnemy({ behaviorPresetId: "none.hold", fsmPresetId, group })
→ spawnEnemy resolves explicit FSM before default `enemyDefinition.behaviorGraphId`
→ entity.fsm runtime is created for each member
```

## Patch

- Moved the FSM selector container from `enemyControls` to the shared `spawnSection`, so it remains available for both single and group spawns.
- Changed FSM selector option refresh to use the live `CONTENT.userFsmPresets.registry()` instead of the stale combined registry list snapshot.
- Added `DevSummonerBrowserGroupFsm.smoke.ts`, which mounts DevSummoner with a lightweight DOM, toggles group mode, selects through the actual compact controls, clicks the actual Spawn Group button, captures `SPAWN_ENEMY_GROUP`, and runs the payload through SpawnSystem.

## Payload proof

The new smoke asserts the DOM-clicked group payload contains the selected `fsmPresetId` and does not write that FSM ID into `behaviorPresetId`.

## Runtime proof

The new smoke passes the captured browser payload through the real SpawnSystem group handler and asserts every live group member has `getFsmDebugSnapshot(entity).presetId` equal to the selected explicit FSM, has a concrete FSM state id, keeps the selected Type, keeps group metadata, and keeps `behaviorId === "none"` for group movement ownership.

## Built-in FSM result

`red` + group + built-in `fsm.hover` produces group members whose runtime preset id is `fsm.hover`.

## User FSM result

A newly created user FSM preset appears in the actual FSM selector via the live user registry; `red` + group + that user preset produces group members whose runtime preset id is the user preset id.

## Default behaviorGraphId override result

`fsm_turret` + group + explicit `fsm.hover` produces group members with runtime preset id `fsm.hover`, proving explicit selection wins over the Type default `behaviorGraphId`.

## Group movement ownership preserved

Group members still spawn with `behaviorPresetId: "none.hold"`, retain group metadata, and rely on the group registry/formation path for movement. Individual FSM movement suppression for grouped members is unchanged.

## Invalid explicit ID behavior

The new smoke mutates a captured browser group payload to an invalid explicit `fsmPresetId` and verifies SpawnSystem throws `Unknown explicit fsmPresetId` rather than silently falling back.
