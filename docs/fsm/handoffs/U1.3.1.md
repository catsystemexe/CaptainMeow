# U1.3.1 — Preserve FSM behavior across Basic Setup changes

## Confirmed browser bug

FSM mode preserved `fsmPresetId` in the DevSummoner payload, but `Count > 1` still let the `EnemyGroupRegistry` drive the group anchor through the normal group movement preset. A visible case was selecting `fsm.charge`, spawning `Count = 1`, then changing only Count to `2`: members had the selected FSM runtime, but the formation anchor used default group movement instead of the selected FSM graph.

## Root cause

U1.2/U1.3 propagated the selected `fsmPresetId` to grouped members, and `EnemySystem` intentionally suppressed individual member FSM movement while `ent.group` exists. The missing bridge was the group anchor: `SpawnSystem` always created groups with `movementPresetId`, and `EnemyGroupRegistry.updateAnchors()` always evaluated `EnemyBehaviorDB[group.behaviorId]`. Therefore the selected FSM preset was present on members but ignored by the anchor movement owner.

## Previous ownership model

- Group anchor movement owner: `EnemyGroupRegistry.updateAnchors()`.
- Group anchor behavior source: normal group `movementPresetId` resolved through `EnemyBehaviorPresets`.
- Member movement: `EnemySystem` suppressed individual FSM movement for group-controlled members, then applied group cohesion.
- Position integration owner: `EnemyGroupRegistry.updateAnchors()` integrated the anchor once; `EnemySystem` integrated member positions once after cohesion velocity was written.

## New ownership model

This is a **group anchor FSM** bridge, not a separate controller entity and not member FSM propagation as the movement fix.

For an FSM group spawn, `SpawnSystem` resolves the explicit/default FSM preset before creating the group and passes the resolved preset to `EnemyGroupRegistry.create()`. The group stores one FSM runtime snapshot. During `updateAnchors()`, the group evaluates that FSM and writes the anchor velocity/movement intent; the existing group anchor integration path integrates the anchor once. Members continue following formation offsets through the existing cohesion path.

## FSM state owner

`EnemyGroupRegistry` owns one `FsmRuntimeSnapshot` per FSM-controlled group. That runtime provides one active state, one state age, one transition evaluation path, and one movement runtime for the group anchor.

## Group anchor movement owner

`EnemyGroupRegistry.updateAnchors()` remains the group anchor movement owner. For FSM groups it evaluates `updateResolvedFsm()` and `executeFsmMovement()` on the group runtime instead of the normal movement preset behavior.

## Position integration owner

`EnemyGroupRegistry.updateAnchors()` remains the only group anchor position integration owner. FSM evaluation produces a target/velocity only; it does not separately integrate the anchor.

## Member movement suppression

Member FSM movement suppression remains unchanged. Group members may still hold FSM runtimes for state/combat continuity, but `EnemySystem` marks their movement runtime suspended while their group exists and then applies `EnemyGroupRegistry.applyMemberCohesion()`.

## Spawn contract

`SPAWN_ENEMY_GROUP.fsmPresetId` is now resolved for the group anchor as well as for members. `behaviorPresetId` remains unrelated to FSM. For FSM group spawns, `SpawnSystem` passes `none.hold` as the group movement preset fallback because the selected FSM runtime is the behavior source.

## Preset precedence

For group spawns the runtime precedence is:

1. explicit `fsmPresetId` on the group spawn payload,
2. authored enemy default `behaviorGraphId`,
3. no FSM group anchor runtime; normal group movement preset applies.

Invalid explicit `fsmPresetId` throws `[SpawnSystem] Unknown explicit fsmPresetId: ...` before creating a group and does not silently fall back to default group movement.

## Basic Setup precedence

Basic Setup remains an orthogonal configuration layer. It may change appearance/type, count, formation, spacing, elasticity, baseSpeed draft data, and spawnY, but it does not select or replace the FSM preset/graph.

## Type / Appearance behavior

Changing Type/Appearance changes the spawned enemy template/appearance while preserving the selected FSM preset ID and graph.

## Count-change behavior

`Count = 1` emits a single enemy with the selected `fsmPresetId`. `Count > 1` emits a group with the same `fsmPresetId`; the group anchor owns the selected FSM runtime and members follow the anchor as a formation. Returning to `Count = 1` again spawns one enemy with the same selected FSM preset.

## Formation / Spacing / Elasticity interaction

Formation, spacing, and elasticity continue to configure member offsets and cohesion around the anchor. They no longer imply any behavior reselection or default group movement replacement in FSM mode.

## Speed / baseSpeed behavior

`baseSpeed` remains draft/preset data only in this session. U1.3.1 tests identity continuity and draft persistence for Speed/baseSpeed without claiming a runtime speed multiplier effect.

## Y / spawnY behavior

Y/spawnY continues to set spawn position/anchor position through the existing UI-to-runtime mapping. Changing Y does not alter selected FSM preset or graph identity.

## Preset and graph identity continuity

The new runtime smoke proves Basic Setup edits preserve `FsmPresetEditorModel.selectedId` and the selected persisted graph object identity. Only explicit preset selection changes behavior.

## Invalid preset behavior

Invalid explicit FSM group IDs throw a typed runtime error and leave no empty group behind. They do not use normal/default group movement as a fallback.

`FsmGroupAnchorBehavior.smoke.ts` verifies:

- Count `1` resolves `fsm.charge` on a single enemy.
- Count `2` resolves `fsm.charge` on the group anchor runtime.
- FSM groups store `none.hold` as the group movement fallback and do not use default group movement.
- After real `EnemySystem` updates, the FSM group anchor transitions to `straight.charge` movement and moves differently from a default `none.hold` group.
- Both members remain at formation offsets around the moving anchor.
- Member FSM movement remains suspended while group-controlled.
- Basic Setup edits preserve selected preset and graph identity.
- Invalid explicit FSM group IDs throw clearly and leave no group behind.
