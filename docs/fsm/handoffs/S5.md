# S5 — Movement composition MVP

## Session commit

The commit containing the S5 implementation.

## Goal

Implement the MVP FSM movement-composition runtime on top of S4 formal entries: one existing movement preset base, ordered `sineOffset`/`clampY` modifiers, group-control suppression, and cull-reference capability for the FSM path.

## Starting S4 movement path

- FSM movement was bridged through `getLegacyMovementPresetId` and `EnemySystem.applyStateBehavior`.
- Formal entry deleted `fsmAppliedMovementPresetId` so the legacy bridge re-applied the active preset.
- `EnemySystem` remained the single velocity/application and position-integration owner.
- Group members still computed individual movement before cohesion overwrote velocity.
- Non-group culling used `EnemyCullReference.resolveMovementCullReferenceX`, which special-cases cyclic behavior IDs.

## Implemented scope

- Added state-scoped `FsmMovementRuntime` creation on every formal entry.
- Added a `movementPreset` base adapter over existing behavior preset data and behavior modules.
- Added ordered `sineOffset` and `clampY` modifier execution.
- Routed FSM movement output to the existing EnemySystem velocity handoff and integration owner.
- Suppressed individual FSM movement for live group-controlled enemies.
- Added FSM-path cull-reference resolution through active movement runtime.
- Added focused movement-composition and group-movement smoke tests.

## Movement pipeline

- Formal entry resolves the state's `movement.base` once.
- The `movementPreset` base adapter creates entity-local behavior runtime state.
- Per non-suppressed tick, the base updates state and writes one mutable target.
- Modifiers run in schema array order and mutate the same target.
- `EnemySystem` converts the final target to velocity.
- Existing EnemySystem integration updates position exactly once.

## State-scoped movement runtime

- Base runtime stores preset ID, behavior ID, cloned params, behavior-local state, and cull-reference capability.
- Modifier runtime stores type, cloned params, and entity-local state.
- `target` is a reusable mutable `{ x, y }` scratch object.
- Every formal entry, including spawn and self-transition, replaces `runtime.movement`.
- No-transition ticks reuse the same movement runtime.
- Multi-entity runtime state is not shared.

## sineOffset semantics

- Parameters: `ampX`, `ampY`, `freqHz`.
- Runtime state: `phase`, initialized to `0` on formal entry.
- Application: add `sin(phase) * ampX` and `sin(phase) * ampY` to the current target.
- Advancement: `phase += 2π * freqHz * dt` after application.
- Group suppression skips updates, so phase is paused while suppressed.

## clampY semantics

- Parameter: `paddingPx` from the S1 descriptor.
- Runtime state: none beyond an empty entity-local state object.
- Application: preserve X and clamp target Y to `[paddingPx, logicH - paddingPx]`.
- Validation: S1/S5 descriptor validation still enforces numeric range and the existing max modifier count; no `minY/maxY` schema exists in this branch, so `E_CLAMP_Y_RANGE` is not applicable.

## Group-controlled movement policy

- Detection uses runtime `ent.group.groupId` plus the active `EnemyGroupRegistry` lookup.
- When group-controlled, FSM base update and modifiers are skipped.
- Group cohesion remains the movement owner for velocity.
- FSM transitions, state age, and combat selection continue.
- No blending is introduced.

## Cull-reference policy

- FSM movement runtime exposes `entityPosition` or `moduleAnchor`.
- Existing cyclic movement behaviors (`sine`, `loop`, `orbitTarget`) map to `moduleAnchor`.
- Other movement presets use `entityPosition`.
- FSM culling asks `getFsmMovementCullReferenceX` instead of hard-coding the active preset ID.
- Legacy non-FSM and group culling still use `EnemyCullReference.resolveMovementCullReferenceX`.

## Compatibility removed

- FSM `EnemySystem` path no longer calls `applyStateBehavior`.
- FSM movement no longer depends on `fsmAppliedMovementPresetId` to initialize or reset movement.
- FSM movement no longer changes entity `behaviorId`, `behavior`, or root `bState` on each state.

## Compatibility retained

- `getLegacyMovementPresetId` remains exported for S3/S4 compatibility tests and external callers.
- `fsmAppliedMovementPresetId` cleanup remains in formal entry as a harmless legacy field cleanup.
- `EnemyCullReference.ts` remains for non-FSM and group culling compatibility.
- Existing movement behavior modules and preset JSON remain the source of movement behavior.
