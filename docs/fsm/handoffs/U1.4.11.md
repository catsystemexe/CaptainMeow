# U1.4.11 — Basic Speed source of truth and zero semantics

## Confirmed browser evidence

The session targeted the confirmed `User FSM Turret` evidence:

- Preset states: `enter → straight.basic`, `attack → none.hold`, `retreat → straight.charge`.
- The visible Basic Speed slider could show approximately `115` while runtime diagnostics sometimes showed `baseSpeed: 0`.
- After editing, slider `320` reached diagnostics as `baseSpeed: 320`, and slider `0` reached diagnostics as `baseSpeed: 0`.
- The invalid behavior was that explicit zero still allowed translational raw preset velocity: `straight.basic` could show `effectiveSpeed: 0` while moving at about `-160`, and `straight.charge` could show `effectiveSpeed: 0` while moving at about `-520`.

## Previous ambiguity

A5 correctly identified that Basic Speed `0` became a runtime fallback case, but U1.4.11 narrows that into an implementation fix. The ambiguous behavior was caused by two separate source/semantic gaps:

1. The FSM preset editor draft normalized Basic Setup for display, but the FSM authoring draft loaded the raw preset clone. If raw/canonical preset data was missing or differed from the normalized editor Basic Setup, the slider/editor draft and authoring SPAWN override could diverge.
2. Runtime speed scaling used `null` as the missing-speed compatibility sentinel, but `fsmBaseSpeed()` also converted numeric zero into `null`. `velocityFromFsmTarget()` then skipped scaling and returned raw movement-preset velocity.

## Canonical Basic Speed source

For U1.4.11, the canonical source is the normalized FSM preset Basic Setup object:

```text
preset.definition.basicSetup.baseSpeed
```

The UI/editor path now initializes both the editor model and authoring model from normalized Basic Setup data. Runtime diagnostics `baseSpeed` means the runtime canonical Basic Setup speed used by the spawned FSM.

## Preset-load synchronization

`FsmPresetAuthoringModel.load()` now normalizes `cloned.basicSetup` with the same `normalizeBasicSetup(..., "fsm")` path already used by `FsmPresetEditorModel.loadDraft()`.

This makes preset selection/load initialize these from one normalized object:

```text
visible Basic Speed slider
editor draft basicSetup.baseSpeed
authoring draft preset.basicSetup.baseSpeed
SPAWN override definition.basicSetup.baseSpeed
runtime diagnostics baseSpeed
```

## Missing versus explicit zero

Missing values and explicit zero are now distinct:

- Missing or null runtime `baseSpeed` remains the compatibility fallback sentinel (`null`).
- Explicit numeric `0` is preserved as a finite runtime speed.
- Legacy presets with missing Basic Setup are normalized at the dev authoring boundary to the FSM default Basic Speed, currently `115`.

## Runtime zero semantics

Runtime now preserves explicit zero:

```text
baseSpeed = 0
→ fsmBaseSpeed(...) = 0
→ fsmEffectiveSpeed(...) = 0 × activeState.speedMultiplier = 0
→ velocityFromFsmTarget(...) returns { x: 0, y: 0 }
```

This prevents `effectiveSpeed = 0` from falling through to raw movement preset velocity.

## Movement scaling formula

For finite effective speed:

```text
effectiveSpeed = runtimeBasicSetupBaseSpeed × activeStateSpeedMultiplier
```

Then:

- if `effectiveSpeed === 0`, final velocity is exactly zero;
- if the active movement has a nonzero reference speed, raw movement velocity is multiplied by `effectiveSpeed / referenceSpeed`;
- if no reference speed exists but target displacement exists, target direction is normalized to `effectiveSpeed`;
- only missing/null/invalid effective speed uses the raw compatibility fallback.

## Monotonic scaling

`FsmBasicSpeedMonotonicScaling.smoke.ts` verifies deterministic monotonic scaling for `straight.basic` and `straight.charge` at Basic Speed values:

```text
0, 50, 100, 200, 300
```

The test asserts:

```text
speed(0) = 0
speed(50) < speed(100) < speed(200) < speed(300)
```

## State carry

`FsmBasicSpeedThreeStateCarry.smoke.ts` verifies:

```text
enter   → straight.basic
attack  → none.hold
retreat → straight.charge
enter   → straight.basic
```

For Basic Speed `0`, `115`, and `320`, diagnostics retain the selected runtime baseSpeed in every state and recompute effectiveSpeed as base × state multiplier. Returning to `enter` preserves the same global Basic Speed.

## Hold-state interpretation

`none.hold` remains zero motion for every Basic Speed. Diagnostics still retain the selected Basic Speed and effectiveSpeed. Zero movement in a hold state is movement semantics, not Basic Speed loss.

## Diagnostics semantics

Diagnostics retain the data field `baseSpeed`, but the rendered label is now explicit:

```text
Basic Speed (runtime) baseSpeed
State Speed × speedMultiplier
Effective Speed effectiveSpeed
```

This keeps compatibility with existing smoke text checks while clarifying that `baseSpeed` is the runtime canonical Basic Setup speed for the spawned FSM.
