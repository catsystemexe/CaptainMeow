# FSM S10 — State and Transition Authoring Handoff

## Goal
S10 adds form/list authoring for user FSM presets in Enemy Lab. It covers preset metadata, states, movement base, ordered modifiers, targeting, combat, lifecycle enter actions, ordered transitions, live diagnostics, and explicit Save/Cancel through `UserFsmPresetStore`.

## Starting S9 capabilities
S9.2 provided schema-v1 built-ins, immutable built-in registry data, `UserFsmPresetStore`, combined registry refresh, preset CRUD/import/export/spawn, and Enemy Lab runtime mounting. It did not include state/transition authoring, a node graph, or S11 preview workflow.

## Authoring draft model
`src/dev/FsmPresetAuthoringModel.ts` introduces `FsmPresetAuthoringDraft` with `originalPresetId`, cloned schema-v1 `preset`, `selectedStateId`, `dirty`, and live `diagnostics`. Drafts use the canonical `FsmPresetSchemaV1`; no second schema was introduced.

## Preset metadata
User drafts can edit metadata name and description. Initial state is edited against current state IDs and validated by the existing FSM validator.

## State operations
Supported model operations: add, duplicate, rename, label edit, delete, reorder, and select. Generated state IDs are deterministic (`state`, `state-2`, ...). Built-in mutation attempts are rejected.

## State ID rewrite semantics
State rename validates the new ID, rejects collisions, updates the state ID transactionally, rewrites all transition targets from the old ID to the new ID, and updates `graph.initialStateId` when needed while preserving state order.

## Deletion policy
`planDeleteState` reports incoming transitions and whether confirmation is required. Confirmed deletion removes incoming transitions targeting the deleted state so valid operations do not leave dangling targets. If the initial state is deleted, the first remaining state becomes initial; if no states remain, the draft remains invalid.

## Movement editor
S10 keeps movement base focused on the current `movementPreset` schema type. The UI exposes the preset ID field, and the model writes the canonical `movement.base` shape.

## Modifier editor
The model supports add/remove/reorder/type-change/param edits for current descriptor-backed modifier types: `sineOffset` (`ampX`, `ampY`, `freqHz`) and `clampY` (`paddingPx`). Modifier array order remains runtime evaluation order.

## Targeting editor
The model and UI support current targeting modes only: `forward` and `atPlayer`. Changing targeting writes the canonical targeting config and does not invent params.

## Combat editor
Combat supports `disabled`, `inherit`, and `profile`; profile mode writes `profileId` and allows the existing validator to report missing or invalid profile data.

## Lifecycle editor
Lifecycle supports ordered `despawn` enter actions only. The existing validator surfaces terminal-state warnings when despawn actions coexist with outgoing transitions; transitions are not silently removed.

## Transition editor
Each state has ordered transition operations for add, duplicate, delete, reorder, target edit, condition type edit, and condition param edit. Condition type changes reset params to descriptor defaults while preserving the target. Self-transitions are allowed; dangling targets remain validation errors and block save.

## Validation pipeline
Every draft mutation recomputes diagnostics with `validateFsmPreset`. Diagnostics retain severity, code, path, message, and existing contextual location metadata. Errors block save; warnings allow save.

## Save / Cancel / dirty policy
Save is explicit and goes through `UserFsmPresetStore.upsert`. Cancel reloads the persisted preset and discards the draft. Dirty state is explicit. Built-ins cannot save. No autosave was added.

## Built-in read-only behavior
Built-in presets load into a cloned read-only draft so their graph details remain visible. Authoring mutations return `E_BUILTIN_READONLY`. Enemy Lab labels built-ins as `BUILT-IN / READ ONLY`; existing Duplicate remains available through the preset management controls.

## Runtime/spawn separation
Unsaved drafts are separate cloned objects and do not update the combined runtime registry. After valid save, `UserFsmPresetStore` refreshes the combined registry, and spawning uses the persisted preset definition. Spawn paths do not read storage directly.

## Risks / inputs for S11
- The S10 UI is intentionally compact and form/list based; S11 can build preview affordances on top of the draft model without making drafts authoritative runtime data.
- S11 should preserve the invariant that unsaved drafts never affect spawn/runtime behavior.
- If S11 adds richer condition/modifier controls, it should continue reading descriptor params instead of duplicating option lists.
