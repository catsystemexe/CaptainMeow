# U1.4.8 — Synchronize Basic Setup into FSM authoring draft

## Confirmed A2 root cause

A2 proved that Basic Setup edits stopped at the split between `FsmPresetEditorModel.draft.basicSetup` and `FsmPresetAuthoringModel.draft.preset.basicSetup`. Manual SPAWN resolves `currentDraftFsmOverride()` from the authoring draft, so unsaved editor-only Basic Setup changes were not present in the override sent to SpawnSystem.

## Previous split ownership

Before U1.4.8, Basic Setup UI changes called `presetModel.setBasicSetup(...)` and updated the editor draft only. The authoring draft still held the loaded preset definition. Runtime speed code correctly applied whatever value it received, but it received the old authoring-draft value.

## Chosen normalized source of truth

`FsmPresetEditorModel.setBasicSetup(...)` remains the single normalization point for Basic Setup UI edits. `DevSummoner` now reads the normalized `presetModel.draft.basicSetup` object and passes that exact object into the authoring model, avoiding separate normalization in two UI paths.

## FsmPresetAuthoringModel mutation

`FsmPresetAuthoringModel.setBasicSetup(next: EnemyLabBasicSetup)` was added. It normalizes/clones the Basic Setup object, writes `draft.preset.basicSetup`, and uses the existing `mutate()` path so the graph, selected state, preset identity, validation, and dirty semantics are preserved.

## DevSummoner edit path

`editFsmBasicSetupDraft()` now performs:

```text
UI control values
→ presetModel.setBasicSetup(...)
→ presetModel.draft.basicSetup normalized value
→ authoringModel.setBasicSetup(normalized value)
→ renderPresetEditor()
```

`currentDraftFsmOverride()` still reads `authoringModel.draft.preset`.

## Dirty-state semantics

Changing Basic Setup Speed, Count, Formation, Spacing, Elasticity, or Spawn Y marks the authoring draft dirty for editable user presets. The new DOM smoke asserts the visible dirty badge after a Basic Speed edit.

## Single draft Speed proof

`FsmBasicSetupDraftSynchronization.smoke.ts` mounts the Enemy Lab, creates an editable user FSM preset, changes the real `#ds-fsm-base-speed` input to `150`, clicks the actual SPAWN button at Count `1`, and verifies the emitted `SPAWN_ENEMY` payload contains `resolvedFsmPresetOverride.definition.basicSetup.baseSpeed === 150`. It then runs the payload through SpawnSystem and EnemySystem and verifies the first authoritative movement tick reports a speed of approximately `150`. The same flow verifies Speed `60` without Save.

## Group draft Speed proof

The same DOM smoke changes Count to `3`, changes Basic Speed to `200`, clicks SPAWN, verifies the emitted `SPAWN_ENEMY_GROUP` payload carries `baseSpeed === 200`, runs SpawnSystem/EnemySystem, verifies the group anchor speed is approximately `200`, and verifies the runtime group has three members.

## State multiplier DOM-path proof

The smoke changes `#ds-fsm-state-speed` through the actual input event, clicks SPAWN, and verifies the resolved active state carries `speedMultiplier` values `0.5` and `2`. It verifies single speed changes to approximately `50` and `200` at Basic Speed `100`, and verifies the Count `3` group anchor speed is approximately `200` when the multiplier is `2`.

## Other Basic Setup field synchronization

The DOM smoke changes formation to ring, spacing to `44`, elasticity to `6`, and spawnY to `123`. It verifies the resolved override `definition.basicSetup` contains those same values. It also verifies the runtime group payload keeps the selected formation/spacing ownership and maps spawnY to the expected runtime anchor Y.

## Saved storage behavior

The smoke snapshots the saved user preset Basic Setup immediately after creating the editable preset and verifies the saved store remains unchanged after unsaved Basic Setup edits and SPAWN. Save is still required for persistence.
