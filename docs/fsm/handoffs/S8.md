# S8 — User preset registry, persistence, import/export, and recovery

## Goal

S8 adds the non-UI domain layer for user-authored FSM presets. It keeps built-in schema-v1 presets immutable and separate, adds a `localStorage`-backed user preset store, deterministic JSON import/export, recovery APIs, and a combined read-only registry view for future S9 UI integration.

S8 does **not** add the visual Enemy Lab editor, graph canvas, form controls, runtime timing changes, movement/combat/lifecycle semantic changes, cloud sync, IndexedDB, or server APIs.

## Starting state

The branch started from the S7.1 snapshot with:

- canonical schema-v1 built-ins in `src/game/content/fsmPresets.json`,
- immutable built-in registry,
- compatibility-only legacy migration,
- resolved runtime snapshots,
- S7.1 transition movement fix,
- retained Dev UI FSM snapshot,
- no user preset persistence,
- no FSM import/export helpers,
- no FSM authoring UI.

The requested focused S1–S7.1 baseline smokes, `npm run typecheck`, and `npm run build` passed before patching.

## Storage key and envelope

Storage key:

```text
captain-meow.fsm.user-presets.v1
```

Envelope:

```ts
interface UserFsmPresetStorageV1 {
  storageVersion: 1;
  presets: FsmPresetSchemaV1[];
  updatedAt?: string;
}
```

The store serializes deterministic, pretty JSON and persists schema-v1 definitions only. It never stores resolved runtime snapshots, entity state, selected enemy state, age, movement runtime, combat runtime, or debug snapshots.

Unknown future storage versions fail safely, load no user entries, report diagnostics, and are not overwritten automatically.

## Storage abstraction

S8 introduces:

```ts
interface KeyValueStorage {
  getItem(key: string): string | null;
  setItem(key: string, value: string): void;
  removeItem(key: string): void;
}
```

`UserFsmPresetStore` accepts an injected storage object. If omitted, it checks `window.localStorage` only at store construction time; there is no storage access at module import time. Tests use in-memory storage, and `null` storage is valid for SSR/Node/no-browser environments.

Storage exceptions are converted to structured diagnostics.

## User store API

The domain service lives in `src/game/enemies/fsm/UserFsmPresetStore.ts` and exposes:

- `load()`
- `list()`
- `get(id)`
- `upsert(preset)`
- `delete(id)`
- `clear()`
- `importJson(text, options?)`
- `exportJson(ids?)`
- `replaceFromImport(text, options?)`
- `inspectRawStorage()`
- `registry()`
- `diagnostics()`

Caller inputs are cloned and normalized before storage. Returned presets and resolved snapshots are frozen where practical.

## Validation pipeline

Every user preset entering the store passes:

1. JSON/plain-data parsing or cloning,
2. schema-version check through the existing schema validator/normalizer,
3. existing normalization (`normalizeFsmPreset`),
4. descriptor/reference validation from existing FSM validation,
5. FSM semantic validation from existing FSM validation,
6. movement preset cross-reference validation against content movement preset IDs,
7. built-in ID collision check,
8. user collision policy handling,
9. resolution through `resolveFsmPreset` before acceptance.

The implementation does not add a parallel FSM validator.

## Collision policies

Built-in IDs are reserved. A user preset with a built-in ID is always rejected.

User `upsert` replaces an existing user preset with the same ID.

Import defaults to `reject`. Explicit policies:

- `reject`: reject any existing user ID collision,
- `replace-user`: replace existing user presets with the same IDs,
- `rename`: deterministically suffix only the preset ID (`-2`, `-3`, ...). State IDs and transition targets are not changed.

## Combined registry behavior

`registry()` returns a read-only combined view:

- `get(id)` resolves built-ins or users,
- `list()` returns built-ins first in canonical order, then users sorted by stable ID,
- `sourceOf(id)` returns `builtin`, `user`, or `undefined`.

Built-ins remain immutable. User presets resolve to immutable snapshots. Registry access does not read storage; user entries rebuild only after load/mutation/import/clear.

## Import formats

Accepted formats:

1. single schema-v1 preset,
2. storage envelope `{ storageVersion: 1, presets: [...] }`,
3. supported legacy behavior graph shape, migrated through `migrateLegacyBehaviorGraph()`.

Import text larger than 1 MB is rejected before JSON parsing. Arbitrary JavaScript is not executed.

Legacy imports are migrated to schema v1, validated, and return a migration warning. Legacy input is never executed directly.

## Export format

`exportJson()` exports all user presets as a deterministic schema-v1 storage envelope with pretty JSON.

`exportJson([singleId])` exports a single selected schema-v1 preset object. Multiple selected IDs export a bundle envelope.

Built-ins are excluded by default. Runtime state is never exported.

## Corrupt-data recovery

Startup/load never crashes on:

- missing storage,
- corrupt JSON,
- unsupported storage versions,
- partially invalid bundles,
- storage read/write/remove exceptions.

Corrupt raw storage remains inspectable through `inspectRawStorage()` until explicit `clear()` or `replaceFromImport()` succeeds. Partially invalid bundles load valid entries, report invalid entries, and do not silently rewrite cleaned storage.

## Transactional write behavior

Mutating operations serialize and write first. In-memory state is committed only after the write succeeds. If a write fails, the prior in-memory store and registry remain unchanged.

`clear()` is explicit and uses `removeItem`; failure leaves the current in-memory state unchanged.

## Integration points

- `loadContent()` constructs `userFsmPresets`, calls `load()` once, and exposes `fsmPresets` as the combined registry.
- Canonical built-in loading remains unchanged.
- Built-in enemy graph cross-reference validation remains based on built-in presets only, preserving shipped-content invariants.
- User preset IDs can be resolved through the combined registry API for future programmatic spawning/integration.
- No authoring UI was added.

## Explicitly deferred S9 UI

S8 intentionally does not implement:

- visual editor,
- state-editing forms,
- graph canvas,
- drag/drop,
- authoring UI controls,
- recovery UI.

## Risks and concrete inputs for S9

- S9 should treat `UserFsmPresetStore` as the only persistence boundary and should not call `localStorage` directly.
- S9 can use `registry()` for combined lookup/listing and `sourceOf(id)` for UI labels/permissions.
- S9 should surface diagnostics from load/import/upsert/delete/clear without inventing another validation layer.
- S9 must keep built-ins read-only and route edits through user preset IDs.
- S9 should decide whether UI exports single selected presets or bundle envelopes based on selection count, matching S8 helper behavior.
